# «Честный месяц»: backend MVP

## Быстрый запуск

Требуются Python 3.13+, PostgreSQL, Redis и настройки из `backend/.env.example`.
Существующая инфраструктура также использует MinIO для аватаров/health-check.
JWT-ключи и `.env` не коммитятся. Существующий `docker-compose.yml` поднимает зависимости.

```sh
# Из корня репозитория, после настройки backend/.env и JWT-ключей:
docker compose up --build -d
```

Backend автоматически выполняет Alembic миграции перед стартом.
Прямой адрес: `http://localhost:8080`. Swagger: `/api/docs`, схема: `/api/openapi.json`.

Локально (из `backend`, с доступными PostgreSQL/Redis):

```sh
poetry install
```

Из `backend/src`, с активированным окружением backend:

```sh
alembic upgrade head
uvicorn main:app --host 0.0.0.0 --port 8080
```

## Соглашения для фронтенда

- Все новые маршруты: `/api/v1`. Все поля **snake_case** (OpenAPI — окончательный контракт).
- Деньги — целые копейки `*_minor`, валюта MVP — `RUB`.
- `amount_minor` транзакции: отрицательное число — списание, положительное — поступление.
- `expense_impact_minor`: положительное — расход, отрицательное — уменьшение расходов.
- Время операции обязательно с timezone (`2026-09-20T12:00:00Z`). Аналитика по умолчанию `Europe/Moscow`.
- `start_date` и `end_date` включительно, поддерживается произвольный диапазон до 3661 дня. Параметры календарных дат ограничены 1970–2100 годами.
- Списки событий/операций/внимания: `{items,total,limit,offset}`. Максимум `limit=200`.
- Все финансовые данные изолированы по авторизованному пользователю.
- Ошибки используют существующий формат backend (400/401/403/404/409/413/422).
- Пустой аккаунт возвращает нулевую аналитику и пустые списки.

`DESIGN.MD` учтён: `/dashboard` содержит данные для основной карточки **Total Balance**, карточек счетов, истории и предупреждений. Числа не форматируются в строки: фронтенд сам применяет разделители, валюту и дизайн. Баланс по всем импортированным операциям не равен доходу минус расходам за выбранный период.

## Авторизация

Используется существующая регистрация/авторизация:

```http
POST /api/v1/auth/register
X-Client: mobile
Content-Type: application/json

{"email":"demo@example.com","password":"DemoPassword123!","username":"Demo"}
```

`X-Client: mobile` удобен для Swagger/curl: оба токена в JSON. Для браузера `X-Client: web` (по умолчанию), refresh в HttpOnly cookie, существующая CSRF-механика.
Во все финансовые запросы передавать `Authorization: Bearer <access_token>`.

## Демо за минуту

1. Зарегистрироваться/войти.
2. `POST /api/v1/demo/load` с `{"month":"2026-09-01"}`.
3. `GET /api/v1/dashboard?period=month&date=2026-09-01`.
4. `GET /api/v1/events?type=shared_expense`, затем `/events/{id}` — общий ужин и Money Graph.
5. `GET /api/v1/attention` — поступление 500 ₽ «за обед».
6. Выбрать опцию из `options`, отправить её `action` и `related_event_id` в `POST /events/{id}/resolve` (поле `label` не отправлять).
7. Повторно запросить dashboard/attention/digest: числа и счётчик изменятся.

Загрузка демо идемпотентна: повторный запрос не создаёт дубли и сохраняет решения пользователя.
Демо содержит **70 операций**, из них 69 в выбранном месяце и одна в предыдущем.
Исходник набора: `backend/src/service/finance/providers.py::demo_dataset`.

Контрольные числа до уточнения для сентября 2026:
- расходы: **20 598 ₽** (`2059800`);
- доходы: **95 000 ₽** (`9500000`);
- спорных операций: **1**, неизвестное поступление **500 ₽**;
- выданный долг 3000 ₽ погашен двумя платежами, остаток **0**;
- ужин 8000 ₽ минус четыре компенсации — **1600 ₽**.

После решения `{"action":"income"}` доход увеличивается на 500 ₽, расходы не меняются.
После решения `shared_expense_repayment` с выбранной покупкой расходы уменьшаются на 500 ₽, доход не меняется.

|---|---|---|
| GET | `/banks` | Демо-провайдеры и статус подключения |
| POST | `/banks/{provider}/connect-and-sync` | Подключить демо-банк и импортировать; тело `{"month":"2026-09-01"}` |
| POST | `/banks/{provider}/sync` | Повторить синхронизацию; такое же тело |
| POST | `/demo/load` | Все четыре банка и весь набор одним запросом |

| POST | `/imports` | Импорт JSON, максимум 2000 операций |

| GET | `/events` | События; `type`, `status`, `start_date`, `end_date`, `timezone`, пагинация |

| POST | `/events/{id}/resolve` | Подтвердить классификацию/связь, атомарно пересчитать |

| GET | `/analytics/explanation` | Те же вычисления, `excluded_breakdown` со ссылками на события |
| GET | `/dashboard` | Аналитика + счета/баланс/10 последних событий/3 спорных |
| GET | `/digest?date=2026-09-20` | Дневная сводка, очередь уточнений, непогашенные долги |

Провайдеры: `tbank`, `sber`, `alfa`, `ozon`. Все имеют `mode: "demo"`, обращений к API банка нет.

### Аналитика

```http
GET /api/v1/analytics?period=week&date=2026-09-14
GET /api/v1/analytics?period=year&date=2026-09-01
GET /api/v1/analytics?start_date=2026-09-01&end_date=2026-09-07
```

`period`: `day|week|month|year`. Неделя начинается в понедельник. Явный диапазон имеет приоритет над period/date.
`summary` содержит `bank_outflow_minor`, `bank_inflow_minor`, `real_expense_minor`, `real_income_minor`, `net_income_minor`, `excluded_minor`, `excluded_breakdown`, `categories`, `timeline`, `needs_attention_count`, `unresolved_inflow_minor`, `is_provisional`.
`comparison`: предыдущий календарный месяц/год либо предшествующий диапазон той же длины. Процент `null`, если прошлые расходы равны нулю.

### JSON и CSV

Создать счёт:

```json
{"external_id":"my-card","bank":"tbank","name":"Основная карта","account_type":"card","opening_balance_minor":1000000}
```

Отправить операции (account_id заменить результатом создания):

```json
{
  "transactions": [
    {
      "external_id": "operation-001",
      "account_id": "00000000-0000-0000-0000-000000000001",
      "amount_minor": -12500,
      "occurred_at": "2026-09-20T15:30:00+03:00",
      "description": "Покупка",
      "merchant": "Пятерочка"
    }
  ]
}
```

CSV имеет явно заданный универсальный формат, **не произвольный экспорт любого банка**:

```csv
external_id,amount_minor,occurred_at,description,merchant,counterparty
operation-001,-12500,2026-09-20T15:30:00+03:00,Покупка,Пятерочка,
operation-002,9500000,2026-09-20T16:00:00+03:00,Зарплата,,Работодатель
```

Разделитель `,` или `;`, UTF-8/BOM. Обязательны `external_id,amount_minor,occurred_at`; опционально `description,merchant,counterparty,category,transfer_reference,currency`.
Одинаковый `account_id + external_id` с теми же данными пропускается. С изменёнными данными — `409`, весь импорт откатывается. Нужны стабильные ID источника: совпадение суммы/даты само по себе не удаляет реальные одинаковые покупки.

### Подтверждение

```json
{"action":"income"}
```

```json
{"action":"shared_expense_repayment","related_event_id":"00000000-0000-0000-0000-000000000002"}
```

Самостоятельные действия: `expense`, `income`, `debt_given`.
Связанные: `own_transfer`, `debt_repayment`, `shared_expense_repayment`, `refund` — требуют `related_event_id`.
Ответ: обновлённое `event` (после объединения ID может стать ID исходной покупки), `needs_attention_count`, `refresh` — списки данных для повторного запроса.
Подтверждение хранится на исходной операции, а не на временной проекции, поэтому переживает повторный sync.

## Модель денег и правила

1. Перевод себе: две противоположные суммы на собственных разных счетах, интервал ≤2 дней и подтверждающее назначение/одинаковый `transfer_reference`. Неоднозначные пары автоматически не склеиваются.
2. Marketplace: пополнение — перевод, покупки — расходы с категориями; FIFO-ссылки `funding_links` показывают, какое пополнение финансировало покупку, без повторного учёта суммы.
3. Долг: выдача не расход; возвраты связаны по контрагенту/назначению, не доход; сумма погашений ограничена остатком.
4. Общая покупка: компенсации уменьшают расход в дату их поступления. Автоматическое связывание — единственная подходящая ресторанная покупка за 7 дней. При нескольких кандидатах требуется подтверждение.
5. Неизвестное поступление не включается в доход: `needs_attention`, `is_provisional`, отдельная сумма неизвестных поступлений. Неизвестный исходящий перевод временно учитывается расходом.
6. Возврат товара связывается с покупкой по продавцу и доступной сумме; частичные возвраты поддерживаются. Он уменьшает расходы, а не увеличивает доходы.
7. **Наличные: расход сразу при снятии.** Отдельный кошелёк наличных не ведётся; повторный импорт наличных покупок не поддерживается.

Все итоги получаются из **датированных вкладов событий** (`contributions`). Покупка в августе и возврат в сентябре: август положительный расход, сентябрь отрицательный. Поэтому любые непересекающиеся дневные/недельные срезы, точно покрывающие месяц, складываются в месячный итог. Полные календарные недели, выходящие за границы месяца, сначала нужно обрезать.

`expense_impact_minor` в карточке события — эффект всей истории события. Если часть компенсаций вне выбранного периода, для итогов использовать `/analytics`, а не суммировать карточки.
Баланс счёта = `opening_balance_minor + сумма импортированных signed amount_minor`. Это баланс по доступной истории, не подтверждённый живым банковским API.

## Регулярное использование

Рабочая backend-механика: ежедневный `/digest` + `/attention` с конкретными действиями + `/resolve` с немедленным пересчётом. На обычный день — **0 ручных действий над операциями** после загрузки данных, неоднозначная операция — **1 подтверждение**. Файловый импорт требует отдельной загрузки файла, демо-sync — нажатия кнопки. Фоновая синхронизация с реальными банками и push-уведомления не заявляются.

## Проверки

Из `backend`:

```sh
poetry run pytest tests/unit -q
```

Финансовые HTTP-тесты используют реальный async SQLAlchemy и изолированную SQLite БД; auth dependency заменена тестовым пользователем. Они проверяют импорт, откат, повторную синхронизацию, owner isolation, решения, граф, OpenAPI. Чистые тесты ядра проверяют кейс и периодную арифметику.
Существующие integration-тесты auth требуют PostgreSQL, Redis и MinIO; запускаются через прежний `docker-compose.test.yml`.
